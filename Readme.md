Вкладки и функционал
Навигация — нижняя панель из 5 вкладок (Navigation.tsx): Калькулятор, HUD, История, Зарядка, Настройки. HUD-вкладка держится смонтированной постоянно (App.tsx), чтобы GPS-трекинг, таймер и накопленная дистанция не сбрасывались при переключении на другие вкладки.
1. Калькулятор (CalculatorTab.tsx)
Два независимых режима работы:
Быстрый расчёт по SoC — ввод start/end SoC, дистанции, типа дороги (город/трасса/смешанный), температуры, состояния климата → получаем расход кВт⋅ч/100км, км/кВт⋅ч, стоимость по выбранному тарифу, эквивалент в литрах бензина и экономию.
Планировщик маршрута — ввод адресов А→Б (или произвольная дистанция), приложение:
геокодирует адреса (Nominatim),
строит маршрут через OSRM (расстояние + профиль скорости по шагам маршрута),
семплирует маршрут по расстоянию и запрашивает профиль высот (Open-Meteo Elevation API, с кэшем),
запрашивает прогноз погоды в нескольких точках вдоль маршрута на расчётное время прибытия в каждую точку,
считает расход посегментно (estimateSegmentedRouteConsumption, см. ниже) — с учётом локального рельефа, погоды и относительного ветра в каждом отрезке маршрута, а не одного усреднённого значения на весь маршрут.
После расчёта показывается карта маршрута (RouteMap.tsx, Leaflet) и разбивка энергии по факторам (скорость / температура / ветер / осадки / стиль / рельеф / климат).
Карточка «Оптимальная скорость» — см. раздел 11.
«What-if» пересчёт при выборе другой плановой скорости без повторных сетевых запросов.
Сохранение рассчитанной поездки в Историю одним нажатием.
2. HUD (GPS-спидометр) (HudTab.tsx, самый крупный компонент)
Живой спидометр на navigator.geolocation.watchPosition с фильтрацией шума GPS (порог точности, сглаживание скорости и высоты, отсечение неправдоподобных скачков дистанции/скорости).
Live SoC / запас хода, пересчитываемые по мере движения — расход накапливается по каждому пройденному GPS-сегменту на его фактической скорости (см. раздел 10), а не по средней скорости поездки.
Живой набор/сброс высоты по данным GPS-альтиметра (с шумоподавлением) → рекуперация/подъём учитываются в реальном времени.
Классификация стиля вождения в реальном времени (currentTripStyle) — по стабильности скорости (стандартное отклонение), соотношению максимальной и средней скорости («рваный» темп) и доле времени на высокой скорости (>105 км/ч). Даёт множитель 0.75–1.35 к расходу и метку («Эко», «Сбалансированный», «Динамичный», «Агрессивный» и т.п.).
Погодный бейдж — подтягивает текущую погоду (температура/ветер/осадки/город) по первой полученной GPS-точке.
Компас относительного ветра — встречный/попутный/боковой ветер относительно текущего курса движения (по компасу устройства/GPS heading).
Прогноз SoC в пункте назначения — по адресу (с построением маршрута, весь тот же пайплайн, что в Калькуляторе) или по произвольной дистанции по прямой (упрощённая temporal-оценка без карты дорог).
Wake Lock — устойчивое удержание экрана включённым во время трекинга (с обходами для iPhone/Safari).
Старт / Стоп / Сброс поездки, сохранение завершённой поездки прямо в Историю с итоговыми параметрами (дистанция, средняя/макс. скорость, энергия, стиль вождения — пишется в заметку поездки).
3. История (HistoryTab.tsx)
Список всех сохранённых поездок с фильтрами по типу дороги и поиском.
Графики динамики расхода (recharts: area chart расход/км⋅кВт⋅ч по времени).
Общая статистика: суммарный пробег, суммарная экономия vs бензин, и т.д.
Значок стиля вождения за всё время (calculateHistoricalDriverStyle) — сравнение среднего расхода с эталоном BENCHMARK_CONSUMPTION_KWH_100KM.
Коррекция финального SoC прямо в Истории (без пересчёта прогнозной модели): ползунок 0..startSoc, быстрые кнопки ±10, автоматический пересчёт энергии/расхода/стоимости/экономии по уже сохранённому тарифу поездки; поездка помечается endSocAdjustedManually.
Импорт/экспорт: полный бэкап в JSON (exportBackupJSON) и экспорт таблицы поездок в CSV (exportSessionsCSV, с BOM для корректной кириллицы в Excel).
Быстрое добавление поездки вручную (модалка AddTripModal.tsx).
4. Зарядка (ChargingTab.tsx)
Два режима ввода: по целевому SoC (текущий % → целевой %) или вручную в кВт⋅ч.
Учёт потерь на зарядке (% от sta анции: gross = net / (1 - loss%)) — заряд, «взятый» со счётчика станции, всегда больше, чем реально попавший в батарею.
Выбор тарифа из пресетов (домашняя AC, домашняя ночная, быстрая DC, Маланка DC/AC, Evika, BatteryFly, Zaryadka день/ночь/AC/DC) или свой тариф.
Итоговая стоимость зарядки по gross-кВт⋅ч, оценка добавленного запаса хода.
5. Настройки (SettingsTab.tsx)
Ёмкость батареи, валюта, региональный пресет тарифов (Беларусь / Россия, REGION_PRESETS) с автозаполнением всех тарифов.
Ручная настройка каждого тарифа отдельно.
Эквивалент расхода бензина (л/100км) и цена топлива — база для расчёта экономии.
Тема оформления (тёмная/светлая), хаптик-обратная связь.
Экспорт/импорт полного бэкапа (настройки + история), сброс к дефолтным значениям.
6. Админ-панель (AdminPanel.tsx)
Доступна только пользователю с ролью admin. Позволяет создавать и удалять обычных пользователей приложения (хранятся в Upstash Redis, пароли — scrypt-хэши). Открывается по значку щита в шапке (Header.tsx).
Модель расхода энергии — алгоритмы
Вся физика расхода живёт в src/utils/storage.ts и переиспользуется одинаково между Калькулятором, HUD и планировщиком маршрута, чтобы цифры не расходились между экранами.
1. Базовая кривая скорость → расход
interpolateVigoSpeedConsumption(speedKmH) — единая кривая «скорость → кВт⋅ч/100км» без учёта погоды/рельефа/стиля:
15–70 км/ч: кусочно-линейная интерполяция по калибровочным точкам [30, 11.2], [50, 12.0], [60, 12.8], [70, 13.5].
70–105 км/ч: гладкая кубическая кривая через опорные точки 70=13.5, 80=14.2, 100=17.9, 105=19.3 кВт⋅ч/100км — начиная примерно с 80 км/ч аэродинамическое сопротивление становится доминирующим компонентом нагрузки, поэтому кривая заметно круче линейного участка.
>105 км/ч: непрерывная квадратичная ветвь (энергия ∝ v²), «пришитая» без разрыва к значению в 105 км/ч. Калибрована по реальному заезду владельца (77.7 км, ~105 км/ч средняя, +25…29°C, климат выключен, штиль, показания бортового компьютера 21.4 кВт⋅ч/100км) — это калибровочный якорь, а не заводское значение Cd.
Скорость всегда ограничивается диапазоном 15–150 км/ч перед подстановкой в формулу.
Общая калибровка: результат всей кривой домножается на константу VIGO_SPEED_CURVE_CALIBRATION_SCALE = 0.96 (−4%) — введена после сверки с реальными маршрутами владельца, показавшими, что модель немного завышала расход по всему диапазону скоростей. Форма кривой (включая точку 95–100 км/ч) сохранена, изменён только общий масштаб.
Опорные точки после калибровки (кВт⋅ч/100км):
Скорость, км/ч	30	50	60	70	80	90	95	100	105	120	150
Расход	10.75	11.52	12.29	12.96	13.63	15.04	16.02	17.18	18.53	22.39	31.64
2. Температура батареи (холодовой штраф)
Физическое (не HVAC) сопротивление ячеек батареи на холоде — насыщающаяся экспонента, а не линейный рост без предела:
degreesBelowComfort = max(0, 18 − T)
tempMultiplier = 1 + 0.30 × (1 − e^(−degreesBelowComfort / 48))
Асимптотический потолок +30% при экстремальном холоде — реальный пакет не теряет неограниченно много эффективности линейно с падением температуры.
3. Осадки и состояние дороги
calculatePrecipitationImpact(weatherCode, precipitationMm) — код погоды WMO (Open-Meteo) + интенсивность осадков:
Снег (коды 71/73/75/77/85/86 и диапазон 70–79): +8% (лёгкий) → +14% → +18% → +22% (сильный снег/накат), зависит от мм/ч.
Ледяной дождь (56/57/66/67): фиксировано +18% (гололедица).
Дождь: непрерывная шкала от +2% (морось, ≤0.1 мм/ч) до +12% (ливень, >6 мм/ч), с минимальным полом +10% для «тяжёлых» WMO-кодов (65/81/82/95/96/99) даже если мгновенное значение мм/ч мало.
Туман (45/48): +2%.
Сухо: 0%.
Сезонные (долгосрочные) суточные осадки конвертируются в часовой эквивалент перед подстановкой в модель, чтобы мм/сутки не приняли за мм/ч.
4. Ветер (относительная воздушная скорость)
Ветер моделируется не как процентная надбавка к полному расходу, а через относительную воздушную скорость (v13/v14 модели, см. WIND_MODEL_V12.md…WIND_PRECIPITATION_MODEL_V14.md):
rad = relativeWindAngle × π/180        // 0° = встречный, 180° = попутный
longitudinal = windSpeed × cos(rad)
lateral      = windSpeed × sin(rad)
relativeAirSpeed = √((v + longitudinal)² + lateral²)
Только аэродинамическая доля базового расхода (плавно растущая с 22% до 55% с ростом скорости) домножается на (relativeAirSpeed / v)²; неаэродинамическая часть (качение, электроника) ветром не затрагивается. Для попутного ветра действует пол в 78% от базового расхода — чтобы сильный попутный ветер не делал более высокую скорость выгоднее низкой только за счёт формулы. Итоговый множитель ограничен диапазоном [0.78, 1.60].
На маршруте локальный курс (bearing) считается для каждого отрезка отдельно (не одно направление А→Б на весь путь), а вектора ветра усредняются через sin/cos-компоненты, а не как обычные углы.
5. Рельеф (подъёмы/спуски и рекуперация)
Физика E = m·g·h, с КПД привода на подъёме и КПД рекуперации на спуске:
масса         = 1600 кг   (curb weight ~1526 кг + допуск на водителя/багаж)
climbKwh      = m·g·gainM / 3.6e6 / 0.90     // 90% КПД трансмиссии на подъёме
descentCredit = m·g·lossM / 3.6e6 × 0.65     // 65% реально возвращается рекуперацией
netKwh        = climbKwh − descentCredit
Нормализуется в кВт⋅ч/100км и ограничивается диапазоном [−8, +15], чтобы шум GPS/API высот не давал неправдоподобных выбросов. Набор/сброс высоты считается с порогом шума (3 м для маршрутов, 1.5 м по умолчанию в общей утилите computeElevationGainLoss) — мелкие колебания профиля не накапливаются как «реальный» перепад.
Один и тот же набор физических констант используется и в storage.ts (estimateTripConsumption), и в services/routeElevation.ts (calculateElevationEnergy), поэтому расчёт рельефа даёт одинаковый результат независимо от того, откуда он вызван — живой трек HUD (сырые метры GPS-альтиметра) или планировщик маршрута (OSRM + Elevation API).
6. Климат-контроль (HVAC / тепловой насос)
HVAC моделируется как электрическая мощность в кВт, а не фиксированный процент — энергия маршрута = мощность × фактическая длительность поездки в часах (а не × дистанция), потому что климат-контроль работает по времени, а не по километражу.
19–23°C: базовая нагрузка ~0.4 кВт (вентиляция/поддержание).
Ниже 19°C — модель теплового насоса с поддержкой ТЭНа (кривая планирования, не измеренная телеметрия VIGO):
Температура	Мощность
+10°C	~0.82 кВт
+5°C	~1.06 кВт
0°C	~1.30 кВт
−5°C	~1.60 кВт
−10°C	~1.90 кВт
−15°C	~2.30 кВт
−20°C	~2.70 кВт
−25°C	~3.25 кВт
−30°C (потолок)	~3.80 кВт
Тепловой насос несёт основную часть нагрузки, ТЭН подключается всё больше при усилении мороза. На длинных поездках средняя мощность немного снижается (до пола 92%) — вклад начального прогрева/ТЭН менее значим после стабилизации салона.
Выше 23°C: компрессор A/C, растущая линейно нагрузка (потолок 2.6 кВт).
В посегментном расчёте маршрута (estimateSegmentedRouteConsumption) добавлена кривая прогрева салона: первые ~25 минут поездки мощность HVAC умножается на коэффициент, плавно спадающий с 1.4× до 1.0× — прогрев холодного салона ощутимо прожорливее поддержания уже комфортной температуры.
Легаси-эквивалент в кВт⋅ч/100км (climateDeltaKwh100, при условной скорости 60 км/ч) сохранён только для обратной совместимости UI, реальный расчёт маршрута всегда идёт через мощность × время.
7. Стиль вождения
Три независимых источника, в порядке приоритета:
Явно переданный фактор (customDriverStyleFactor) — например, live-фактор из HUD (currentTripStyle.factor) при построении прогноза «SoC в пункте назначения» во время активной поездки.
История за последние 30 дней (≥2 валидных поездок, расход 8–35 кВт⋅ч/100км):
Если есть ≥2 поездки с извлекаемым HUD-фактором «стиль поездки: xN.NN» в заметке — усредняются напрямую эти факторы (диапазон 0.75–1.35).
Иначе — средний расход за месяц сравнивается с эталоном BENCHMARK_CONSUMPTION_KWH_100KM = 14.5, но используется только 35% отклонения, с жёстким ограничением [0.92, 1.08] — исторический расход уже включает погоду/рельеф/HVAC того периода, поэтому 1:1 использовать его как постоянный множитель стиля означало бы двойной учёт этих эффектов.
Вся история (если за месяц <2 поездок, но всего есть ≥2) — тот же принцип 35%-калибровки, диапазон [0.92, 1.08].
Иначе — нейтральный фактор 1.0.
Итоговый фактор всегда ограничен диапазоном [0.75, 1.35].
8. Итоговая формула (estimateTripConsumption)
flatRoad = baseSpeedConsumption(v) × tempMultiplier × windMultiplier × precipMultiplier
estimatedConsumption = flatRoad × driverStyleFactor
                        + elevationDeltaKwh100
                        + climateDeltaForRoute
где climateDeltaForRoute = climatePowerKw × durationHours / distanceKm × 100 (перевод мощность×время в эквивалент кВт⋅ч/100км для данной поездки). Результат ограничен диапазоном [9.5, 34.0] кВт⋅ч/100км как защита от вырожденных входных данных. Функция также возвращает подробную разбивку по каждому фактору (speedImpactPct, temperatureImpactPct, windImpactPct, precipitationImpactPct, elevationImpactPct, climateImpactPct) для UI.
computeFlatRoadConsumptionRate(...) — переиспользуемая функция, вычисляющая именно «плоскодорожную» часть (шаги 1–4) отдельно от рельефа и климата (которые аддитивны и не зависят от скорости движения по конкретному отрезку). Ей пользуются и estimateTripConsumption, и живой посегментный расчёт в HUD — чтобы обе модели не могли разойтись между собой.
9. Посегментный расчёт маршрута (estimateSegmentedRouteConsumption)
Вместо одного усреднённого расчёта на весь маршрут, энергия считается отрезок за отрезком между соседними точками профиля высот/маршрута:
Локальный курс (bearing) — по каждому отрезку отдельно.
Погода — интерполируется между ближайшими запрошенными точками прогноза вдоль маршрута (линейно для температуры/осадков/скорости ветра, циркулярно для направления ветра).
Скорость сегмента — берётся из профиля скоростей OSRM (по факту время/дистанцию каждого шага маршрута — так городские и трассовые участки не усредняются в одну «плоскую» скорость), затем масштабируется так, чтобы средневзвешенная по времени скорость совпадала с плановой скоростью пользователя.
Рельеф, ветер, осадки, стиль, климат (с кривой прогрева) — для каждого отрезка через estimateTripConsumption.
Итог — сумма энергии по всем отрезкам плюс разбивка по вкладам каждого фактора (для отображения в UI), с балансирующим «остатком» (residual), чтобы сумма факторов точно сходилась с итоговой энергией.
10. Live-расчёт SoC в HUD (по сегментам GPS-трека)
До недавнего обновления живой расход в HUD считался как дистанция × расход_на_средней_скорости_поездки. Поскольку кривая скорость↔расход выпуклая (аэродинамика растёт быстрее линейной), это занижало расход на смешанных поездках город+трасса — короткий быстрый участок «размывался» усреднением.
Теперь каждая принятая GPS-точка (валидный сегмент трека) добавляет в накопитель энергию, рассчитанную по своей фактической скорости на этом отрезке (computeFlatRoadConsumptionRate), с учётом актуальной погоды/ветра/осадков/live-стиля вождения:
segmentEnergyKwh += (segmentDistanceKm / 100) × [
  baseSpeedConsumption(segmentSpeed) × tempMultiplier × windMultiplier × precipMultiplier × styleFactor
]
Рельеф и HVAC по-прежнему считаются «оптом» за всю поездку и добавляются к накопленной сегментной энергии один раз:
рельеф — потому что это чистая m·g·h от суммарного набора/сброса высоты, независимая от порядка прохождения отрезков;
HVAC — потому что это мощность × прошедшее время, тоже линейно и порядок-независимо.
energySpentKwh = liveSegmentEnergyKwh + elevationEnergyKwh + climateEnergyKwh
Финальная энергия сохранённой поездки при остановке трекинга берётся из этого же уже точного накопленного значения, а не пересчитывается заново по средней скорости.
11. Оптимальная скорость
После расчёта маршрута в Калькуляторе доступна карточка «Оптимальная скорость»:
Перебираются скорости 50, 55, …, 120 км/ч (15 кандидатов).
Для каждой — полный пересчёт посегментной энергии маршрута (estimateSegmentedRouteConsumption) с текущими погодой/ветром/осадками/рельефом/калибровкой стиля/HVAC.
Минимизируется суммарная энергия маршрута в кВт⋅ч, а не кВт⋅ч/100км — поэтому HVAC (энергия которого растёт с временем в пути) делает слишком низкие скорости невыгодными: климат-контроль просто работает дольше.
Расчёт полностью локальный — не делает дополнительных запросов к API маршрута/погоды/высот.
Это справочная модель, а не рекомендация превышать разрешённую скорость на дороге.
Источники данных
API	Назначение	Особенности
Open-Meteo Forecast API	Операционный почасовой прогноз погоды (0–16 дней)	Выбирается час, ближайший к расчётному времени прибытия в точку
Open-Meteo Seasonal API (ecmwf_seamless)	Долгосрочный (сезонный) прогноз, до ~217 дней (~7 месяцев)	Суточные агрегаты (среднесуточная температура/осадки/ветер); приложение никогда не подменяет недоступную дату ближайшей доступной — явно возвращает «недоступно»
Open-Meteo Elevation API	Профиль высот вдоль маршрута	Батчи до 100 точек за запрос; кэш в localStorage на 30 дней по округлённым координатам А/Б; суточный cooldown до полуночи UTC при HTTP 429
OSRM (router.project-osrm.org)	Построение автомобильного маршрута А→Б + профиль скорости по шагам	Публичный демо-сервер, без ключа
Nominatim (OpenStreetMap)	Геокодирование адреса → координаты	Публичный, без ключа
GPS устройства (navigator.geolocation)	Живой трекинг в HUD	Сглаживание скорости/высоты, фильтр по точности и правдоподобности скачков
Семплирование маршрута для запроса высот тарировано по длине маршрута (≤100 км → до 75 точек, ≤300 км → до 100, длиннее → до 200), чтобы вместе с батчами по 100 точек редко требовалось больше 1–2 запросов к API высот на маршрут.

Ключ	Содержимое

Импорт/экспорт полного бэкапа (exportBackupJSON) и таблицы поездок в CSV (exportSessionsCSV) — оба доступны из Истории и Настроек.
Авторизация и админ-доступ
Серверная часть — только Vercel Serverless Functions в api/:
POST /api/auth/login — логин/пароль → scrypt-проверка пароля из Redis (@upstash/redis), выдаётся HMAC-подписанная сессионная кука (evigo_session, 7 дней).
GET /api/auth/me — проверка текущей сессии по куке.
POST /api/auth/logout — сброс куки.
GET/POST/DELETE /api/admin/users — список/создание/удаление обычных пользователей; доступно только роли admin.
Администратор задаётся переменными окружения (ADMIN_LOGIN / ADMIN_PASSWORD), а не записью в Redis — то есть учётку админа нельзя удалить или заблокировать через саму админ-панель. Обычные пользователи хранятся в Redis со scrypt-хэшами паролей; удаление пользователя немедленно делает недействительной его сессию при следующей проверке.
Требуемые переменные окружения (Vercel → Production, см. AUTH_SETUP.md):
UPSTASH_REDIS_REST_URL
UPSTASH_REDIS_REST_TOKEN
AUTH_SECRET          # ≥32 случайных символа
ADMIN_LOGIN
ADMIN_PASSWORD       # ≥8 символов, сравнивается точно (без кавычек в значении)
Секреты не должны попадать в GitHub или клиентский код.
Деплой
Основная платформа — Vercel (vercel.json): фреймворк vite, все не-/api/* маршруты переписываются на index.html (SPA).
Альтернатива — Netlify (netlify.toml): npm run build → публикация dist/, SPA-редирект /* → /index.html. На Netlify серверные функции api/* (авторизация) работать не будут без отдельной адаптации под Netlify Functions.
Локальный dev/self-host — server.ts: Express, в dev режиме отдаёт Vite middleware, в prod — статику из dist/ плюс несколько служебных роутов для скачивания zip-архивов дистрибутива/исходников и /api/health для проверки живости (Cloud Run-совместимый health-check).
Скрипты package.json:
npm run dev      # tsx server.ts — dev-сервер с Vite middleware
npm run build     # vite build + сборка server.ts в dist/server.cjs (esbuild)
npm start         # node dist/server.cjs — production
npm run lint       # tsc --noEmit — проверка типов без сборки
Известные ограничения и допущения модели
Кривая расхода на высоких скоростях (>80 км/ч) калибрована по единственному реальному заезду владельца, а не по паспортному Cd автомобиля — по мере накопления новых трассовых поездок в журнале модель может уточняться.
Оценки мощности HVAC (тепловой насос + ТЭН) — планировочная кривая, не измеренная телеметрия VIGO.
Долгосрочный (сезонный) прогноз погоды — оценка масштаба региона (SEAS5/EC46 через Open-Meteo), не точный почасовой локальный прогноз, и не bias-corrected.
Рельеф из Elevation API/GPS-альтиметра может содержать шум; применяются пороги шумоподавления (1.5–3 м) и жёсткие ограничения итогового вклада рельефа (−8…+15 кВт⋅ч/100км), но на очень коротких или холмистых участках возможны неточности.
Историческая калибровка стиля вождения по журналу поездок работает надёжно от ~2 валидных записей за период; при малом количестве данных модель откатывается к нейтральному фактору 1.0.
Планировщик и Оптимальная скорость не делают дополнительных запросов к внешним API при переборе гипотетических скоростей — расчёт полностью локальный на уже загруженных данных маршрута/погоды/высот текущего запроса.
